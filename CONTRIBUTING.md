# Contributing

Help make the reference clearer, more accurate, and easier to use with an assistant. Small corrections and contrary evidence are valuable.

For a catalog change, state the concept, relevant trust boundary, observable evidence, nearest existing entry, primary sources, and a plausible competing explanation. Describe which source sections you checked. Use measured language about untested settings and preserve existing IDs. Put speculative ideas in a private research card first; they can become public proposals once their supporting material is suitable to share.

For a bug, provide a small invented example. Keep working prompts, attack payloads, private transcripts, personal data, tokens, actual competition records, and source filenames out of issues and pull requests. Public examples should teach evidence interpretation without reproducing an operational attack. Links to primary research are appropriate; copying its attack appendices is not.

The default interface is for reading and review. Avoid adding mandatory manual fields. Give assistants a documented, validated way to maintain records, and keep the person's decisions easy to inspect.

Run the checks listed in README.md. Changes to catalog or web sources require rebuilding both generated pages. Use text APIs for untrusted strings, HTTPS source URLs, and the existing offline architecture. Keep public build inputs explicit. Explain what a test establishes rather than claiming the repository is universally secure.

Contributions to original code and catalog text use the MIT license. Preserve third-party attributions and do not copy text whose license does not permit it.
